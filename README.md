# 达人投放工作台

一个用于管理达人投放记录、并基于投放数据做效果分析的全栈应用，采用 monorepo 结构：

- `frontend/`：React 18 + Vite + Ant Design + React Router v6 + Axios + xlsx
- `backend/`：Node.js + Express + better-sqlite3 + cors
- 数据库：SQLite 文件型（`backend/workbench.db`，首次启动自动创建数据表）

当前为 **V2 播放量口径**：看板、达人汇总、投放管理、Excel 导入导出、AI 校验统一使用「7日播放量 + 累计播放量」两个指标，不再使用「首发播放量 / 次周播放量」的旧语义。

## 播放量字段语义（V2，已冻结）

| 技术字段（数据库） | 正式业务含义 | 说明 |
| --- | --- | --- |
| `first_play` | **7日播放量** | 内容发布约 7 天时记录的累计播放量 |
| `second_week_play` | **累计播放量** | 最近一次更新时的累计播放量，可后续继续更新 |

> `second_week_play` 只是历史技术字段名，**不再代表「第二周新增播放量」**。数据库字段名保持不变，以兼容历史数据与历史 Excel。

## 核心指标定义

| 指标 | 口径 / 公式 |
| --- | --- |
| 后续新增播放量 | 累计播放量 − 7日播放量（仅当两者都有值且 累计 ≥ 7日 时展示，否则显示 `-`） |
| CPM / 平均CPM | 总花费 ÷ 累计播放量 × 1000 |
| 7日CPM | 总花费 ÷ 7日播放量 × 1000 |
| 爆款 / 爆款数 | 累计播放量 ≥ 100000 |
| 7日爆款 / 7日爆款数 | 7日播放量 ≥ 100000 |
| 爆款率 | 爆款数 ÷ 有有效累计播放量的投放数 |
| 7日爆款率 | 7日爆款数 ÷ 有有效7日播放量的投放数 |
| 平均播放量 | Σ有效累计播放量 ÷ 有效累计播放样本数 |
| 总花费 | 范围内所有投放记录 `total_cost` 之和 |
| 投放达人数 | 范围内达人昵称去重数量 |
| 投放次数 | 范围内投放记录条数 |

口径要点：

- **总播放 = Σ累计播放量**。不再使用 `first_play + second_week_play`——两个字段都是累计值，相加会重复计数。
- 单条 CPM / 7日CPM 在分母为空或为 0 时显示 `-`（不参与计算）。

## 数据规则（空值 / 0 / 异常）

- **空（未填写 / null）** = 未采集、待更新。例如累计播放量留空，表示这条内容还没有更新最新播放。
- **0** = 真实观察值，不是缺失。`7日播放量 = 0` 是合法数据，会计入 7日指标的有效样本。
- **异常数据**：`累计播放量 < 7日播放量` 视为自相矛盾的异常记录。
  - 仍计入：总花费、投放次数、投放达人数、7日播放量聚合、7日CPM、7日爆款
  - 不参与依赖累计播放量的指标：累计播放量聚合、CPM、爆款、平均播放量、后续新增播放量
  - 原始数值仍保留在表中（界面标红并给出悬浮提示），便于排查
- 写入校验（新增 / 编辑 / 批量导入 / API 直连一致）：`时间周期`、`达人昵称`、`总花费`、`发布日期` 必填；`总花费 = 0` 合法；当 7日播放量与累计播放量同时有值时，「累计播放量 < 7日播放量」会被拒绝，提示「累计播放量不能小于7日播放量，请检查数据是否录入正确」。

## 功能列表

- **数据看板（Dashboard）**
  - 主口径固定为「按投放周」：累计播放量取各条内容最近一次更新的累计播放量
  - 核心卡片：累计播放量、总花费、平均CPM、投放达人数
  - 辅助指标：7日播放量、后续新增播放量、7日CPM、播放数据已更新 X / Y（含待更新、异常提示）
  - 图表：达人播放量占比、爆款类型分布（爆款 / 7日爆款）、投放周趋势
  - 「按发生周」口径当前**暂未开放**（原因见「当前已知限制」）
- **达人汇总（CreatorSummary）**
  - 核心指标：达人数、投放次数、总花费、累计播放量、平均CPM、爆款数、爆款率、平均播放量
  - 辅助指标：7日播放量、后续新增播放量、7日CPM、7日爆款数、7日爆款率
  - 按达人类型分组展示，支持「最小投放次数」筛选与达人对比（2~5 位）
- **投放管理（Records）**
  - 新增 / 编辑 / 删除 / 分页查询
  - 筛选：时间周期、博主类型、发布日期范围、达人昵称模糊搜索，支持多条件组合
  - 表格指标：CPM、7日播放量、累计播放量、后续新增播放量
- **导入历史（ImportHistory）**：只读的导入批次日志
- **Excel 批量导入**：拖拽上传 → 逐行逐列校验 → 自动去重 → **AI 智能校验**（可选，DeepSeek 逐条判定，可一键修正）→ 确认导入
- **Excel 导出**：按当前筛选条件导出记录明细 / 达人汇总明细 / 达人对比（在前端本地生成）
- **后端健康检查**：前端启动时自动检测后端连通状态（页面右上角状态标签）

## 环境要求

- Node.js 18+（推荐 20 / 22；前端 Vite 5 要求 Node 18+，better-sqlite3 使用预编译二进制、无需本地编译工具）

### 导入规则

- **累计播放量可以留空** → 表示「待更新」，允许导入
- **累计播放量 < 7日播放量** → 该行被拒绝导入（提示：累计播放量不能小于7日播放量，请检查数据是否录入正确）
- **总花费必填**；`总花费 = 0` 合法；空白 ≠ 0（空值是缺失，0 是真实观察值）
- 日期兼容 `2024-07-22`、`2024/7/22`、`2024.7.22` 及 Excel 日期序列号，导入时自动归一化为 `YYYY-MM-DD`
- 金额自动去掉货币符号、千分位（如 `¥5,000` → `5000`）；播放量支持千分位与 `x.x万` 写法（如 `8.2万` → `82000`）
- 链接无协议但形如域名时自动补全 `https://`
- 自动去重：按「时间周期、达人昵称、博主类型、达人主页、植入链接、视频链接、总花费、7日播放量、累计播放量、发布日期」判定；与库中已有记录重复或文件内重复的行会被标记为无效并跳过
- 上传后先预览前 5 条并做行级校验，必填缺失 / 格式错误的行会显示**具体行号与原因**，确认后仅导入通过校验的行

## 导入历史（ImportHistory）

- 导入历史是**只读日志**：当前没有「删除历史」「撤销导入」功能
- 删除真实的投放记录时，系统会清理 `import_batch_records` 映射，但**不会改写当时的批次历史统计**
- 时间在数据库中按 **UTC** 存储，前端按浏览器本地时间展示

## DeepSeek 接入（可选，AI 智能校验功能需要）

### 1. 获取 API Key

1. 访问 DeepSeek 开放平台 https://platform.deepseek.com ，注册并登录
2. 进入「API Keys」页面，点击「创建 API Key」
3. 复制以 `sk-` 开头的密钥（**只在创建时完整显示一次**，请立即保存）
4. 平台需充值或领取免费额度后才可以调用

### 2. 配置

```bash
cp backend/.env.example backend/.env
# 编辑 backend/.env，填入真实密钥
DEEPSEEK_API_KEY=sk-你的真实密钥
```

配置后重启后端，验证是否生效：

```bash
curl http://localhost:3001/api/ai/status
# 返回 {"code":200,"data":{"available":true,...}} 表示已生效
```

> 未配置密钥时后端会打印降级提示，AI 校验自动跳过，**不影响基础导入功能**。

### 3. AI 导入功能使用指南

1. 投放管理页 → 点击「导入Excel」→ 上传 `.xlsx` / `.xls` 文件
2. 上传前可展开「高级规则」，勾选判定规则或填写自定义自然语言条件
3. 上传后自动进入 AI 校验（显示「AI正在判定数据...」加载动画）
4. 校验完成后展示统计（共/通过/警告/错误）与每条记录的问题、修正建议、AI修正值
5. 点击「一键修正」应用 AI 修正值 → 「确认导入」完成导入
6. 只有警告时可点「忽略警告，直接导入」；存在未修正错误时需先修正
7. 未配置 Key 或 AI 调用失败时自动降级：提示「AI校验失败，将跳过智能判定」，可直接按普通导入流程确认导入

AI 判定使用的业务语义与上文一致：`first_play` = 7日播放量、`second_week_play` = 累计播放量，实际CPM 按累计播放量计算，且「累计播放量 < 7日播放量」会被判为错误。

### 4. 支持的判定规则

| 规则标识 | 说明 |
| --- | --- |
| `creator_type_cpm` | 达人类型CPM匹配（如美妆类CPM不超过50，超限标红并建议不再投放该达人） |
| `time_cycle_format` | 时间周期必须符合 `YYYY-Wxx` 格式，不合法自动给出修正值 |
| `duplicate_check` | 相同达人昵称 + 相同发布日期判定为重复，保留首条 |
| `magnitude_check` | 播放量与总花费的量级商业逻辑合理性 |
| `platform_link_match` | 从链接识别平台（抖音/小红书/B站等）并与博主类型匹配 |

自定义规则示例（每行一条，自然语言，优先级最高）：

```text
美妆类达人CPM不应超过50，超过则标红提示
总花费超过10万的记录需要重点审核
```

智能补全（始终开启）：根据昵称推测博主类型、从链接提取平台信息、自动修正日期/数字格式，结果写入 `corrected` 字段，可一键应用。

### 5. 常见问题

- **API 调用失败**：先访问 `/api/ai/status` 确认 Key 已生效；检查网络能否访问 `api.deepseek.com`；前端会自动降级为普通导入，基础功能不受影响
- **额度不足**：DeepSeek 返回余额不足/402 时接口会给出友好提示；请到开放平台充值或领取免费额度后重试
- **请求超时**：单批校验上限 1000 条，超时后可减少单批数量或稍后重试（前端提供「重试AI校验」按钮）
- **校验结果不准确**：可在「高级规则」中补充自定义自然语言条件细化判定
- **页面提示「AI未配置」**：右上角状态标签显示 AI 服务状态，配置 Key 并重启后端后自动变为「AI已就绪」

## 时间周期规则

- 存储格式：`time_cycle` 统一为 `YYYY-Wxx`（如 `2026-W33`），数据库结构未改动
- 周规则：每周从**周一**到**周日**；每年第 1 周从当年**第一个周一**开始（如 2026-W01 = 01/05-01/11）
- 默认业务年份：2026，可通过环境变量修改：`BUSINESS_YEAR=2027 npm run server`
- 时间计算统一在后端完成（`backend/utils/dateCycle.js`），前端只负责展示
- `/api/records/cycles` 返回每个周期的 `weekCode`、`startDate`、`endDate` 和 `label`（如 `08/10-08/16`）
- 查询接口支持 `weekCode` 筛选（兼容旧的 `timeCycle` 参数），周码未补零时自动归一化（`2026-W5` → `2026-W05`）
- 前端展示统一为月日区间：筛选下拉、表格列、新增/编辑弹窗均显示 `08/10-08/16`，表格列悬浮显示完整周数（如 `2026年第33周 08/10-08/16`）
- Excel 导入支持月日区间自动识别为周码（优先匹配已有周期，未收录时按当前年份换算）；导出时间周期列为月日区间格式

## 常见问题排查

### 1. 端口被占用（启动报 EADDRINUSE 或页面打不开）

```bash
lsof -i :3001   # 查看占用后端端口的进程
lsof -i :5173   # 查看占用前端端口的进程
kill -9 <PID>
```

也可换端口启动后端：`PORT=3002 npm run server`（此时需同步修改 `frontend/vite.config.js` 中的代理目标）。

### 2. 依赖安装失败

- 网络问题：`npm config get registry` 查看源，可切换镜像 `npm config set registry https://registry.npmmirror.com` 后重试
- 缓存问题：执行 `npm cache clean --force` 后重新 `npm run install:all`
- better-sqlite3 是原生模块，安装时自动下载预编译二进制；失败通常是因为 Node 版本过旧或网络受限，升级到 Node 18+ 后重试
- 权限问题（EPERM）：检查 npm 缓存目录权限，或指定临时缓存 `npm_config_cache=/tmp/npm-cache npm install`

### 3. 页面提示「网络异常 / 后端服务连接失败」

- 确认后端已启动：浏览器访问 http://localhost:3001/api/health，应返回 `{"status":"ok",...}`
- 前端页面右上角有「后端已连接 / 后端未连接」状态标签，可快速判断连通性
- 两个服务需要同时运行：`npm run dev`

### 4. 浏览器打开页面空白

- 确认访问的是 Vite 开发服务器 http://localhost:5173，而不是直接双击 `index.html`
- 强制刷新（Cmd+Shift+R）清除旧缓存

### 5. 修改源码后页面没有更新

本项目在 `frontend/vite.config.js` 中启用了 Vite 文件监听轮询（`server.watch.usePolling`），以规避本机文件系统变更事件偶发丢失导致的模块缓存不刷新；正常保存源码后刷新浏览器即可生效。

## 当前已知限制（V2）

1. **「按发生周」口径暂未开放**：当前只保存「7日播放量」与「当前累计播放量」，没有逐周播放快照，无法准确还原每一周新增播放，因此看板固定使用「按投放周」口径。
2. **`video_link` 没有 server-side 唯一性约束**：数据库中没有 UNIQUE 索引，后端也不做重复校验；当前去重仅在 Excel 导入时由前端按多字段组合指纹完成。
3. **数据库仍保留历史技术字段名 `second_week_play`**：业务语义已经是「累计播放量」，字段名仅为兼容历史数据与历史 Excel 而保留。
4. **数据规模**：当前后端聚合会拉取全量 records（即每个筛选条件的数据窗口内全量数据），在现有数据量下可接受；未来数据量显著增加时，需要优化分页与聚合方式。
5. **导入历史不可撤销**：导入批次只记录日志，没有「删除历史 / 撤销导入」入口。
